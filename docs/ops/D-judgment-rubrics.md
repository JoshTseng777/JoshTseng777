# D｜判斷力外化：rubric 與 checklist

> 30 秒摘要：這份文件把「什麼時候該升級模型、什麼時候算真的做完、什麼時候該停下來問人、
> 什麼訊號代表該換路而不是重試、品質底線怎麼驗」寫成弱模型可以直接照做的判準。
> 本檔建立時 `evidence/` 是空的，**所有例子都是虛構示意例（非實錄）**，之後有真實案例要
> 替換掉虛構例子。

## 本文件不適用情境

- 使用者已經明確講清楚要什麼、驗收條件也講了——直接照做，不需要套 rubric 猶豫。
- 純資訊查詢（例如「這段程式碼在做什麼」）——這是回答問題，不是要不要繼續執行的判斷。
- 任務本身就是本文件說的「該問使用者」的情況之一時，問完拿到答案後直接執行，不用回頭重新
  套一次 rubric。

---

## 1. 何時升級模型

**判準**：同一個子任務，同一等級模型，錯了一次就升級；不要在同一等級重試第二次。
「錯」的定義：輸出違反了交辦時講好的驗收條件（見 C 文件「任務交辦三要素」）。

- **正例**：Haiku subagent 被要求「列出 `src/` 下所有沒有測試的 export 函式，附檔案:行號」，
  結果漏列了一半、也沒附行號 → 驗收條件不滿足 → 立即用 Sonnet 重跑，並把 Haiku 的輸出和
  「哪裡不合格」一起帶給 Sonnet，不要只重複同一句指令再丟給 Haiku 一次。（示意例，非實錄）
- **反例**：Haiku 第一次結果格式差一點（例如行號差了幾行）→ 直接判定「模型不行」升級到
  Opus，跳過 Sonnet 這一級——中間跳級沒有必要，先試中間那一級，除非任務本身就明顯需要高階
  推理（例如需要跨多檔案做架構取捨）。（示意例，非實錄）
- **不適用**：任務本身難度已知超出小模型能力範圍（例如要求對一份含糊需求做架構設計），
  一開始就該直接派高階模型，不需要先"讓小模型試一次再升級"走個過場。

## 2. 何時算真的完成

**判準**：完成 = 驗收條件被滿足 **且** 有人（或某個 agent）實際檢查過，不是自己宣稱。
「型別檢查/lint 過」≠「功能正確」；兩者要分開講。

- **正例**：修了一個 API 回傳格式的 bug，跑了對應的測試案例（或手動呼叫一次 API 看回傳值），
  確認新格式符合預期，才回報「完成」。（示意例，非實錄）
- **反例**：改完程式碼，只跑了 `tsc --noEmit` 沒有報錯，就回報「功能已修好」——型別檢查通過
  不代表邏輯對，這是把兩件不同的事混成一句話講。（示意例，非實錄）
- **不適用**：純文件/註解修改，沒有可執行的行為可驗證——這種情況「讀一遍確認文字通順、
  沒有事實錯誤」就是完成判準，不需要硬套「跑起來看看」。

## 3. 何時該停下來問使用者

**判準**：符合以下任一條就停下來問，不要自己猜一個答案往下做：

1. 有兩種以上合理的實作方式，選哪個會影響使用者之後怎麼用（架構性選擇，不是純技術細節）。
2. 需要做有品味/主觀判斷的決定，而且做錯的代價高（例如要刪除可能還在用的東西、要不要對外
   發布/push 到別人看得到的地方）。
3. 使用者的指示裡有明顯留白或矛盾的地方（例如本任務 prompt 裡原本留白的「最弱消費者是誰」）。

- **正例**：本次任務原始 prompt 裡「最弱消費者：〔待填：Sonnet 或 Haiku〕」是明確留白 →
  應該問。（真實案例，見本次 session 的 `AskUserQuestion` 呼叫記錄於 G 檔）
- **反例**：文件裡該用「範例」還是「示例」這種純用詞選擇，也發起一次 AskUserQuestion——
  這種低風險、可逆、對結果影響極小的選擇不需要停下來問，自己選一個一致用法即可。
  （示意例，非實錄）
- **不適用**：使用者已經在指示裡講明「這幾項你自己決定就好」——即使有多種合理做法，也不用問。

## 4. 什麼訊號代表方向錯了，該換路而不是重試

**判準**：同一個做法試了兩輪還在原地打轉（錯誤訊息重複出現、或每次修好一個又冒出新的同類
問題），就是換路訊號，不要繼續用同一種修法微調第三次。

- **正例**：想用某個 library 的某個函式修一個問題，改了兩次參數還是同樣的錯誤訊息 → 換成
  查一下這個函式的實際簽名/文件，而不是繼續猜第三組參數。（示意例，非實錄）
- **反例**：一次因為打字錯誤（typo）導致的失敗，就直接判定「整個做法不對」大改架構——單次
  低層級錯誤不是換路訊號，先確認是不是低級失誤，排除後再判斷是否真的要換路。（示意例，非實錄）
- **不適用**：問題本身就已知只有一種正確做法（例如語法錯誤只有一種修法），談不上「換路」，
  直接修正即可。

## 5. 品質底線怎麼驗（不能自己驗自己）

**判準**：驗證者不能是產出者本人（同一個 agent 執行任務又驗證自己的任務，等於沒驗證）。

- **正例**：一個 agent 寫完文件後，派一個**沒看過寫作過程的新 agent**去讀這份文件並回報
  「看不懂的地方」「引用的路徑/工具名是否存在」——這是本次任務收尾步驟 1 的做法。
  （真實案例：見本文件所屬任務的收尾流程設計，將於 G 檔記錄執行結果）
- **反例**：同一個 agent 寫完程式碼，自己讀一遍程式碼說「邏輯看起來沒問題」就算驗證完畢——
  這只是重複自己的假設，不是獨立驗證。（示意例，非實錄）
- **不適用**：極小改動且有客觀機器判準（例如格式化工具本身有 exit code 判斷成功/失敗），
  機器判準本身就是獨立驗證，不需要額外再找一個 agent 覆核。

## 待補（下次維護時做）

- `evidence/` 累積案例後，把「示意例（非實錄）」逐一替換成真實案例，並在替換時保留舊的
  虛構例子在註解裡一段時間，觀察新例子是否真的更貼切，貼切則移除舊例。
