# A｜快速診斷：這個 harness 最容易出錯的前三名

> 30 秒摘要：建立本檔時 `evidence/` 是空的，所以以下三項全部是**推測**（根據 Claude Code /
> coding agent 的一般已知失效模式），不是本 repo 的實錄。每項都附一個弱模型能照做的具體修法。
> **下次維護時**：先讀 `evidence/` 裡累積的真實案例，能對應上的就把「推測」改成「引用
> evidence/xxx.md」；對不上的推測，觀察兩輪還是沒出現對應案例就考慮刪除或降級。

---

## 診斷 1：讀太多不必要的內容（token 浪費）— 推測

**現象**：遇到"找某段程式碼在哪"或"這個功能怎麼運作"這類任務時，直接把整個大檔案讀進來，
或用 `cat`/`grep`（bash 內建）掃整個目錄，而不是先用 Grep/Glob 定位再讀需要的片段。

**具體修法（弱模型可照做）**：
1. 找檔案位置用 Glob，找內容用 Grep（帶 `-n` 顯示行號），**不要**用 Bash 跑 `find`/`grep`/`cat`。
2. Read 一個檔案前，先問自己：「我要找的東西大概在檔案的哪一段？」如果檔案超過 300 行且
   目標明確，先用 Grep 定位行號，再用 `Read` 的 `offset`/`limit` 只讀那一段，不要整檔讀入。
3. 如果任務是「瀏覽式探索」（不確定要找什麼、要跨多個檔案比對），不要自己一個個 Read，
   改派 `Explore` 類型的 subagent 去做，自己只收結論。

---

## 診斷 2：失焦 / 任務範圍蔓延（scope creep）— 推測

**現象**：使用者要求一個小修改，模型在過程中「順手」重構了周邊程式碼、加了使用者沒要求的
錯誤處理或抽象層，或者長對話中間被壓縮（compact）後，忘記最初的驗收條件，開始按自己以為
的目標做事。

**具體修法（弱模型可照做）**：
1. 動手改程式碼前，用一句話覆述「使用者要的最小改動是什麼」；如果想加的東西不在這句話裡，
   先不要加。
2. 每個任務開始前，先確認有沒有 G 這類交接檔或 CLAUDE.md 索引可讀；有的話先讀，不要憑自己
   對專案的猜測直接動手。
3. 長任務中途如果對話被系統壓縮過，**下一步先重新讀一次使用者最初的原始需求文字**（如果還在
   上下文裡）或交接檔，再繼續，不要只靠壓縮摘要自己推斷。

---

## 診斷 3：自我認證但沒有真的驗證（宣稱完成 ≠ 真的完成）— 推測

**現象**：改完程式碼後，直接告訴使用者「完成了」，但實際上沒有跑測試、沒有實際執行過那條
路徑、或者把「型別檢查過」等同於「功能正確」。對於模型型號、API 參數等資訊，用訓練記憶
猜一個看起來合理的值，而不是在當下環境裡查證。

**具體修法（弱模型可照做）**：
1. 涉及程式碼修改的任務，收尾前先問自己：「如果現在用戶去跑這段程式，我有沒有實際看過它跑起來？」
   沒有的話，先跑（測試、實際執行、或用 `/verify` 這類技能），再回報完成。
2. 只跑過 lint/typecheck 不能算「功能正確」，回報時要分開講：「型別檢查通過」和「功能已實際驗證」
   是兩件事，不要合併成一句「都測過了」。
3. 任何型號名稱、版本號、額度規則、API 參數，**當下環境能查的一定要查**（讀系統提示、讀設定檔、
   跑指令確認），查不到就照實寫「未確認，建議使用者實測」，不要用記憶裡的舊值填空。
