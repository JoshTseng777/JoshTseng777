# E4｜任務交辦範本：研究／調查型

> 30 秒摘要：這份範本用在「不改程式碼，只回答問題或做選型比較」的研究/調查任務。複製下面
> 「範本本文」，把【】或＿＿＿填掉，整段貼給 subagent 就能用。欄位設計與回報格式對齊
> `C-model-dispatch.md`，「何時該停下來問使用者」對齊 `D-judgment-rubrics.md` 第 3 節，不重複
> 整段抄錄，只留一句判準提示。

## 這類任務常見的陷阱（填範本前先看一眼）

- 回報時一定要區分「查證到的事實」vs「推論/建議」：查證到的事實要附出處（檔案:行號、
  網址、或指令輸出）；不確定、沒查到、或只是合理推測的內容要明確標記「未確認」，
  不能把兩者混成一句話講，讓使用者誤以為推論也是查過的事實。
- 避免用訓練記憶回答會過時的資訊（版本號、定價、API 參數、模型 ID 等）——這類資訊一律要求
  subagent 在當下環境查證（讀當下設定檔/系統提示、或用 WebFetch/WebSearch 查最新來源），
  查不到就照實寫「未確認，建議使用者實測」，不要用記憶裡可能已經過時的舊值填空。
- 研究任務不改程式碼，範圍要明確標示「只回答問題，不動任何檔案」，避免 subagent 在研究過程
  中「順手」動手改起東西來。

【建議 model 與推理強度】
大量資料蒐集/初步彙整用 Haiku 批次做；一般研究與交叉比對用 Sonnet；需要做選型判斷、
權衡取捨這種有品味成分的最終建議才升 Opus/Fable（但最終決策仍由主對話做，subagent
只負責把資訊收集齊全）。具體模型 ID 字串見 C 文件模型對照表，這裡不重複寫死。

subagent 定義裡設的 model，或繼承父層——不會自動幫你選對層級，交辦前務必填）

【驗收條件】
（可檢查、具體，不要用「查清楚了」「研究完」這種模糊詞）
- 每一項事實陳述都附出處（檔案:行號、網址、或指令輸出），沒有出處的一律標記「未確認」。
- 事實與推論/建議明確分兩段寫，不混在同一句。
- ＿＿＿（例：至少比較 N 個選項；涵蓋成本/維護性/效能等固定幾個面向）

【回報格式】
只回結論 + 出處，硬上限 15 行；「查證到的事實」與「推論/建議」分段標示清楚；
長產物（完整比較表、大量原始資料）先存成檔案，回報時只給路徑。

【何時該停下來問使用者，不要自己往下猜】
若遇到以下情況就先回報問使用者，不要自己猜一個答案往下做：查到的資訊互相矛盾且無法自行
判斷哪個可信、或研究結論會導向兩種以上合理選項且選哪個屬於使用者的主觀偏好、或題目本身
定義不清（例如「哪個更好」沒講清楚評判標準）——詳細判準見 D 文件「3. 何時該停下來問使用者」。
