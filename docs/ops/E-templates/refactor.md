# E3｜任務交辦範本：重構型

> 30 秒摘要：這份範本用在「不改變外部行為，只改內部結構/寫法」的重構任務。複製下面
> 「範本本文」，把【】或＿＿＿填掉，整段貼給 subagent 就能用。欄位設計與回報格式對齊
> `C-model-dispatch.md`，「何時該停下來問使用者」對齊 `D-judgment-rubrics.md` 第 3 節，不重複
> 整段抄錄，只留一句判準提示。

## 這類任務常見的陷阱（填範本前先看一眼）

- 驗收條件一定要包含「行為不變」的具體驗證方式：跑既有測試前後對照，或沒有測試的話先手動
  執行一次記錄「重構前的輸出/行為」，重構後再跑一次比對——不能只憑「讀 code 覺得邏輯一樣」
  就宣稱行為不變，這正是驗證不自驗（見 C 文件「6. 驗證不自驗」）要防的事。
- 具體範圍要明確排除「順便修 bug」和「順便加功能」：重構過程中發現的 bug 或想加的功能，
  記錄下來回報，另開任務處理，**不要混進同一個 diff**——重構和加功能分開做，才能各自獨立驗收
  且方便之後 review 或回退。
- 如果重構範圍內完全沒有既有測試覆蓋，先確認怎麼驗證行為不變（例如需不需要先補一組最低限度
  的對照測試），不要在毫無驗證手段的情況下就動手大改。

## 範本本文（複製這段，填空後貼給 subagent）

```
【任務名稱／一句話目標】
＿＿＿（例：把 src/utils/date.js 裡重複的日期格式化邏輯抽成共用函式）

【目標與動機】
（不是只給步驟，要給前提——為什麼現在要重構這段？是為了之後好加功能、還是消除重複、還是
降低某種維護成本？讓 subagent 知道「改到什麼程度算夠」，而不是無止盡地美化下去）
＿＿＿

【已知背景／已排除的做法】
（已經確認過的既有結構、已經試過但不採用的重構方向、這段程式碼目前所有呼叫它的地方，
避免 subagent 重新摸索或漏掉某個呼叫點）
＿＿＿

【具體範圍】
- 這次任務包含：＿＿＿
- 這次任務不包含（scope 外，重構與加功能分開做）：不包含修任何順便發現的 bug（發現了記錄
  下來回報，另開任務）；不包含加任何新行為/新功能；不包含＿＿＿
- 行為基準：＿＿＿（重構前的行為以什麼為準？既有測試、還是需要先手動記錄一次輸出）

【建議 model 與推理強度】
日常重構用 Sonnet；如果是大量重複性的機械式改寫（例如批次替換同一種寫法），可用 Haiku
批次做，再用 Sonnet 收斂檢查行為是否一致；需要判斷「這樣重構會不會影響其他模組的介面」
才升 Opus/Fable。具體模型 ID 字串見 C 文件模型對照表，這裡不重複寫死。
本任務指定：＿＿＿

【驗收條件】
（可檢查、具體，不要用「做好」「處理完」這種模糊詞；一定要包含「行為不變」的驗證方式）
- 重構前後跑同一組測試（或同一組手動操作），結果一致——附跑測試的結果或對照輸出，
  不能只憑讀程式碼判斷。
- ＿＿＿（例：程式碼行數/重複度有沒有具體下降；公開介面簽名是否維持不變）
- 沒有混入任何本次範圍外的 bug 修正或新功能。

【回報格式】
只回結論 + `檔案:行號`，硬上限 15 行；不要貼整段程式碼，只貼必要的單行引用；
長產物（對照輸出、大量測試紀錄）先存成檔案，回報時只給路徑。

【何時該停下來問使用者，不要自己往下猜】
若遇到以下情況就先回報問使用者，不要自己猜一個答案往下做：發現有兩種以上合理的重構方向
且會影響之後的介面設計、或完全沒有測試覆蓋導致無法驗證行為不變、或指示裡對「重構範圍」
有明顯留白或矛盾——詳細判準見 D 文件「3. 何時該停下來問使用者」。
```
