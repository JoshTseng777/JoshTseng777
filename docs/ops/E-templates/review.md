# E5｜任務交辦範本：審查型

> 30 秒摘要：這份範本用在「審核他人或其他 agent 產出的成果」（程式碼、文件、報告皆適用）。
> 複製下面「範本本文」，把【】或＿＿＿填掉，整段貼給 subagent 就能用。欄位設計與回報格式對齊
> `C-model-dispatch.md`，「何時該停下來問使用者」對齊 `D-judgment-rubrics.md` 第 3 節，不重複
> 整段抄錄，只留一句判準提示。

## 這類任務常見的陷阱（填範本前先看一眼）

- 審查者不能是產出者本人：派去審查的 subagent 必須是**沒看過原始產出過程的 fresh-context
  agent**，不能叫寫這份東西的同一個 agent 自己回頭審自己——這等於沒審查，見 C 文件
  「6. 驗證不自驗」。交辦時要明講「你沒有參與過這份產出的製作過程」。
- 審查結果要分兩類講清楚：「正確性問題」（事實錯誤、邏輯錯誤、違反驗收條件、會導致功能壞掉）
  vs「風格/品味建議」（用詞、排版、非必要的偏好），兩者優先級不同，混在一起講會讓使用者
  分不清哪些是必須改的、哪些是可改可不改的。
- 每一項發現都要給具體 `檔案:行號`，**不能只給籠統評語**（例如不能只寫「這段邏輯怪怪的」，
  要寫「`檔案:行號`，怪在哪裡、為什麼算問題」）。

```
【任務名稱／一句話目標】

【目標與動機】
（不是只給步驟，要給前提——這份產出接下來要拿去做什麼用？審查的目的是抓正確性問題還是
連品味都要挑？讓 subagent 知道審查要嚴到什麼程度）

【已知背景／已排除的做法】

【具體範圍】
- 這次任務包含：審查＿＿＿（列出要審的檔案/產出範圍）
- 這次任務不包含（scope 外）：不包含直接動手修改被審查的檔案（審查者只回報問題，
  不自己動手改，除非另外明講要一併修）；不包含＿＿＿
- 審查基準：＿＿＿（依照什麼驗收條件/規格來判斷對錯，附上原始交辦內容或連結）

【建議 model 與推理強度】
一般檔案/程式碼審查用 Sonnet；大量檔案的初步掃描（例如先抓出有沒有明顯遺漏）可用 Haiku
批次做，再用 Sonnet 做細節判斷；涉及架構合理性、品味爭議這類需要判斷力的審查才升
Opus/Fable。具體模型 ID 字串見 C 文件模型對照表，這裡不重複寫死。
本任務指定：＿＿＿

【驗收條件】
（可檢查、具體，不要用「看過了」「審完了」這種模糊詞）
- 每一項發現都附具體 `檔案:行號`，不接受籠統評語。
- 發現明確分成「正確性問題」與「風格/品味建議」兩類分別列出。
- ＿＿＿（例：至少確認每個檔案裡引用的路徑/工具名/指令是否真實存在，不是憑感覺判斷）

【回報格式】
只回結論 + `檔案:行號`，硬上限 15 行；正確性問題與風格建議分兩段列，正確性問題優先列在前面；
長產物（完整審查清單）先存成檔案，回報時只給路徑。

【何時該停下來問使用者，不要自己往下猜】
若遇到以下情況就先回報問使用者，不要自己猜一個答案往下做：發現的問題嚴重到可能推翻整份
產出（要不要整份重做屬於架構性選擇）、或正確性與風格的界線本身有爭議且做錯代價高
（例如涉及要不要刪掉已發布的東西）、或原始交辦的驗收條件本身有明顯留白或矛盾導致無法判斷
對錯——詳細判準見 D 文件「3. 何時該停下來問使用者」。
```
