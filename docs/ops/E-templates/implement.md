# E2｜任務交辦範本：實作／新功能型

> 30 秒摘要：這份範本用在「加一個新功能」「實作某個需求」這類會產出新程式碼的任務。複製下面
> 「範本本文」，把【】或＿＿＿填掉，整段貼給 subagent 就能用。欄位設計與回報格式對齊
> `C-model-dispatch.md`，「何時該停下來問使用者」對齊 `D-judgment-rubrics.md` 第 3 節，不重複
> 整段抄錄，只留一句判準提示。

## 這類任務常見的陷阱（填範本前先看一眼）

- 驗收條件一定要包含「有沒有實際跑過/驗證過」，**不能只寫「程式碼寫完」**——寫完不等於做完，
  見 D 文件「2. 何時算真的完成」：型別檢查/lint 過 ≠ 功能正確，兩者要分開驗、分開講。
- 具體範圍要明確排除「順手重構」：subagent 在實作過程中看到周邊程式碼不順眼，**不要**順手
  改掉，發現問題就記錄下來回報，另開任務處理，不要混進這次的 diff 裡。
- 如果需求本身有模糊或多種合理實作方式，且會影響使用者之後怎麼用，先問清楚再動手，
  不要自己選一個「看起來合理」的設計就開始寫。

## 範本本文（複製這段，填空後貼給 subagent）

```
【任務名稱／一句話目標】
＿＿＿（例：在登入表單加上「記住我」選項）

【目標與動機】
（不是只給步驟，要給前提——這個功能要解決什麼問題、為什麼現在要加？前提錯了，實作再乾淨也是
白做。讓 subagent 在遇到規格沒寫清楚的地方，有依據做出合理判斷，而不是照字面硬套）
＿＿＿

【已知背景／已排除的做法】
（已經確認過的技術限制、已經試過但不採用的實作方式、專案既有的慣例或既有相似功能的位置，
避免 subagent 重新摸索或選一個已經被否決的方案）
＿＿＿

【具體範圍】
- 這次任務包含：＿＿＿
- 這次任務不包含（scope 外，不要順手做）：＿＿＿（例：不包含重構周邊既有程式碼、不包含
  補齊其他無關功能的測試、不包含改動 UI 風格）

【建議 model 與推理強度】
日常實作用 Sonnet；如果任務主要是套用已知模式做大量重複性的樣板程式碼，可用 Haiku 批次做，
再用 Sonnet 收斂檢查；需要做架構取捨（例如影響多個模組的介面設計）才升 Opus/Fable。
具體模型 ID 字串見 C 文件模型對照表，這裡不重複寫死。
本任務指定：＿＿＿

【驗收條件】
（可檢查、具體，不要用「做好」「處理完」這種模糊詞；一定要包含「實際驗證」，不只是「寫完」）
- ＿＿＿（例：新功能符合規格描述的行為）
- 有實際跑過或驗證過（例如：跑對應測試全綠、或手動執行一次看到預期輸出），不能只憑
  型別檢查/lint 過就回報完成。
- ＿＿＿（是否需要新增/更新測試？）

【回報格式】
只回結論 + `檔案:行號`，硬上限 15 行；不要貼整段程式碼，只貼必要的單行引用；
長產物（設計草稿、大量掃描結果）先存成檔案，回報時只給路徑。

【何時該停下來問使用者，不要自己往下猜】
若遇到以下情況就先回報問使用者，不要自己猜一個答案往下做：規格有兩種以上合理實作方式且
會影響使用者之後怎麼用、或需要做有品味/主觀判斷且做錯代價高（例如要動到使用者可能還在用的
既有邏輯）、或指示裡有明顯留白或矛盾——詳細判準見 D 文件「3. 何時該停下來問使用者」。
```
