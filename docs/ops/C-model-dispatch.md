# C｜模型調度守則

> 30 秒摘要：小事自己做，大量讀取/掃描/驗證派便宜 subagent；交辦時一定給「目標、驗收條件、
> 回報格式」三件事；模型名稱用查證過的字串（見下表），不要憑記憶打；subagent 回報硬上限
> 15 行，長產物存檔傳路徑；驗證工作找別的 agent 做，不要自己驗自己。

## 本守則不適用情境

- 使用者已經明講「你直接改就好，不用查證/不用分派」。
- 單一檔案、預期改動 < 20 行、不需要探索多個檔案的小修。
- 高風險或需要品味判斷的最終決策（例如架構取捨、要不要刪除使用者可能還在用的東西）——
  這種事本守則管的是「怎麼收集資訊」，最終判斷仍由主對話（你）做，不外包。

---

## 1. 指揮官不下場

大量讀取、掃 repo、查網頁、批次改檔、跑驗證，一律派便宜的 subagent 去做，主對話只接收結論。
唯一例外：一手材料裡的關鍵證據（例如 `evidence/` 裡的失敗片段、被診斷對象的原始檔案本體）
自己讀，不能只看 subagent 給的摘要——診斷和判斷必須建立在一手材料上。

高階模型（若當下真的在用比較貴的模型）的額度只花在「換便宜模型就會掉品質」的判斷上：
權衡取捨、讀一手證據、審核他人產出、寫最終判斷文字。掃描、查找、批次改寫、初稿撰寫都不算。

## 2. 任務交辦三要素（每次派工都要講清楚這三件事）

交辦 subagent 時，prompt 裡必須包含：

1. **目標與動機**：要做成什麼、為什麼要做（不是只給步驟，步驟前提錯了會白做）。
2. **驗收條件**：什麼樣的結果算通過（例如「這三個檔案都存在且各自可獨立讀懂」「跑 `npm test`
   全綠」「至少引用一個 `檔案:行號`」）。
3. **回報格式**：見下面「回報合約」。

範例（好 vs 不好）：

- 不好：「幫我看一下這個 repo 有什麼問題。」（沒有驗收條件，沒有回報格式）
- 好：「讀 `src/auth/` 底下所有檔案，列出沒有錯誤處理的對外 API 呼叫。驗收條件：每一項都附
  `檔案:行號`；回報格式：條列，最多 15 行，不要貼整段程式碼，只貼一行引用。」

## 3. 模型與推理強度怎麼指定

**已查證的模型 ID 字串**（本 session 系統環境注入，取代使用者原草稿裡的舊值）：

| 別名 | API 模型 ID |
|---|---|
| Fable 5 | `claude-fable-5` |
| Opus 4.8 | `claude-opus-4-8` |
| Sonnet 5 | `claude-sonnet-5` |
| Haiku 4.5 | `claude-haiku-4-5-20251001` |

> ⚠️ 使用者原始 prompt 裡寫的是 `claude-sonnet-4-6`、`claude-haiku-4-5`（無日期後綴），
> 與本表不一致。本表是本 session 環境當下注入的值，判定為較新／較可信，但**模型 ID 會隨時間
> 改版**，之後任何 session 發現呼叫失敗，先查當下環境的系統提示或官方文件，不要照抄本表。

**在 Agent 工具裡指定模型**：`Agent` 工具的 `model` 參數只接受四個通用別名之一：
`sonnet` / `opus` / `haiku` / `fable`（不是完整 API 字串，也没有 `inherit` 這個顯式選項——
省略 `model` 參數就是「用 agent 定義裡設的值，或繼承父層」）。也就是說，**換模型的做法是
呼叫 `Agent({model: "haiku", subagent_type: "general-purpose", ...})` 這種形式，不是去找一個
叫「Haiku agent」的 subagent 類型**——`subagent_type`（做什麼任務）和 `model`（用哪個模型）
是兩個獨立的欄位。

**推理強度（reasoning effort）逐 agent 指定**：機制**已證實存在**——Agent 工具本身的說明文字
明確寫「Each agent type's model, reasoning effort, and tool access are set in its definition
(`.claude/agents/*.md` frontmatter, or the SDK `agents` option)」。但本環境目前沒有任何一份
真實的 `.claude/agents/*.md` 檔案可供讀取比對，**frontmatter 裡確切的欄位名稱未經一手驗證**。
→ 待使用者填：建立第一個 agent 檔案時，實測確認欄位名稱（很可能是 `model` 旁邊的某個
`effort` 或類似鍵），並回填這裡。

## 4. 回報合約（所有 subagent 都要遵守）

- 只回結論與「檔案:行號」，**硬上限 15 行**。
- 禁止把整份檔案內容貼回主對話。
- 長產物（草稿、報告、大量掃描結果）先存成檔案，subagent 回報時只給檔案路徑，不貼內容。

## 5. 升降級路徑

- 小模型（Haiku）錯一次 → 立即升級到下一級（Sonnet），**不重試第二次用同一個模型**。
- 中階模型（Sonnet）同一子任務連錯兩次 → 帶著完整失敗軌跡（錯在哪、已經試過什麼）升級。
- 找到能解的模式之後 → 把做法寫成清楚步驟，降回便宜模型批次套用到同類任務，不要一路用貴模型。
- 同一件事最多重試兩輪（含升級後那一次），兩輪都不行就停下來問使用者，不要無限重試。

## 6. 驗證不自驗

執行任務的 agent 不能是驗證自己成果的 agent。

- 驗證檔案內容：派一個**沒看過原始對話的 fresh-context agent**去做 read-back（重新讀一次
  檔案，確認內容和聲稱的一致）。
- 驗證程式碼：跑測試或實際執行，不要只憑讀 code 就說「看起來對」。
- 高風險或有品味爭議的判斷：找第二意見（另一個 agent 獨立給答案）或多方案讓一個 agent 評審
  挑選，不要單一 agent 自問自答。
